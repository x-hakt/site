## Twenty tabs, none of them open

Playtopia is one of the busier hulls in the fleet: a games community site,
live and earning, where a member can connect their Steam account and pull in
their whole library. Once that is done the site knows what you own, how long
you have played each one, and when you last launched it.

What it did nothing with, until today, was the obvious next thing. Every one of
those games has a stream of official news: a patch on Tuesday, a weekend event,
a roadmap post, a "the servers are down" notice. Steam publishes all of it, but
one game at a time, each on its own page. If you own forty games you are not
checking forty news pages. You find out a game had a big update when you happen
to launch it and something looks different.

And the question you actually have is one Steam does not answer at all: not
"what is the latest news for this game" but "what has changed since the last
time I played it." You put a game down for three months, you want the three
months of changes in one place before you pick it back up.

So that is the feature. A page, [My Game
Feed](https://playtopia.com.au/news/my-games), that gathers the official Steam
news for the games you own, newest first, and flags every item that was
published after you last played. The interesting part is not the idea. It is
that the whole thing had to be built without touching the parts of Playtopia
that matter.

## Why the first version is frontend only

**Why it is here.** Playtopia's staging site, `source.playtopia.com.au`, is not
a full copy of production. It runs its own isolated preview copy of the
frontend, but it points at the same live API and the same live database as the
real site. That is fine for checking how a page looks. It is not fine for
trying out a feature that wants new tables, because there is no safe place to
put them: a migration on staging is a migration on production.

**How it works.** So the rule for the first slice was that it adds no database
tables, no new backend service, and no change to any running production
service. Everything it needs already exists or lives in the browser:

- The list of games comes from an endpoint Playtopia already has,
  `GET /api/v1/gaming/library?platform=STEAM`, the same one the existing
  library page uses. The feature reuses it as-is.
- The news itself comes from Steam's own public API, fetched server-side.
- Which games you pinned, which you muted, and which items you have read are
  kept in `localStorage`, keyed to your user id. During testing that is the
  whole preference store. It is per-browser, and that is a known limit, not an
  oversight.

## One route, fanned out, failure-tolerant

**Why it is here.** The browser cannot call Steam directly for forty games:
that is forty cross-origin requests, no caching, and a pile of Steam's markup
to clean up on the client. It needs one call to Playtopia that comes back with
a clean, sorted list.

**How it works.** There is a single server-side Next.js route,
`POST /gaming/steam-news`. It takes a list of Steam app ids, caps it at 24 per
call, and fans out to Steam's `ISteamNews/GetNewsForApp` endpoint once per
game, all in parallel with `Promise.allSettled` so that one game that is slow
or returns a 500 does not sink the whole batch. What comes back is:

- the news items, with Steam's BBCode and `{STEAM_CLAN_IMAGE}` tags stripped
  out and the text trimmed to a preview length,
- deduplicated, because Steam will return the same post under two feed labels,
- sorted newest first,
- plus a `failedAppIds` list, so the page can say "these three did not load"
  instead of silently dropping them.

Caching is layered: the upstream fetch to Steam is revalidated every 30
minutes (`next: { revalidate: 1800 }`), and the response to the browser is
`private, max-age=300`. The page loads news for your top 18 games on first
visit, prioritised by pinned, then most recently played, then most hours, and a
"load updates from more games" button pulls the next batch.

## The one view that took no code

**Why it is here.** "Since you played" is the whole reason the feature is more
useful than Steam's own news pages, and it is the thing a raw chronological
feed cannot give you.

**How it works.** It is a filter, not a feature. Playtopia already stores
`lastPlayedAt` for every imported game. A news item is "since you played" when
its publish time is later than that timestamp. The feed marks those items and
offers a view that shows only them. No new data, no ranking model, one
comparison.

The rest of the page is presentation: a card layout and a compact monospace
log view, the choice remembered per browser; exact Steam publish times in local
time rather than "3 days ago"; titles that link straight to the source post;
and an artwork fallback chain that tries the stored image, then Steam's icon
hash, then the game's header image, then gives up and shows an emoji.

## How it went live without a rebuild scare

**Why it is here.** The Playtopia frontend is the one container in that stack
with a hard rule around it: it runs a specific, digest-locked image, and it is
not rebuilt, restarted, or replaced without a deliberate, checked promotion.
A new feature does not get to bend that.

**How it works.** The build only ever went to the isolated preview containers
first. `source.playtopia.com.au` served the feature while it was tested and
revised over the afternoon, four or five rounds of it, with the live site
untouched on its existing image the whole time. Promotion to production was its
own step, gated:

- a static-versus-hydrated parity check on the new build,
- capture of the current live image as a named rollback tag and a dated
  baseline before anything changed,
- a guarded promotion, then smoke checks against the live site: the page
  answers, the menu links are present, the Steam route returns real items,
- the new known-good image digest written down as the recorded baseline.

## Verified vs assumed

**Verified.** The page is live at `playtopia.com.au/news/my-games` and answers
200. The Steam route returns real, deduplicated items with no failures for a
test library. Both navigation links are in place, desktop and mobile. The
parity gate and the post-promotion smoke checks passed, and a rollback image
was captured before promotion and is retained.

**Assumed, and deferred on purpose.** That members want owned games in the feed
automatically rather than opting each one in. That recency and playtime are a
good enough sense of importance without any semantic ranking. That per-browser
preferences are acceptable for a test but not for the real thing. The
production version, if the feed proves its worth, is a different shape: one
canonical game record per Steam app id, news stored once and deduplicated by
Steam's own id, follow and read state in the database, background ingestion
that runs per game rather than per user, and catalogue-wide follow so you can
track a game you do not own. None of that is built. This version exists to find
out whether it should be.

The transferable part: when staging shares production's data, the first version
of a feature is the one that asks nothing new of the backend. Reuse the
endpoints that exist, put the new logic in a stateless route, keep user state
in the browser, and design the real storage only once real people have told you
the feature is worth storing.
